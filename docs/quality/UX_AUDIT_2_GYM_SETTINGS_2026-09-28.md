## Findings and coherent implementation groups

### G2-A — Select exact Gym evidence, including two workouts on one day

**Source-confirmed correctness defect, P1.** `GymProgressContent` stores `selectedChartPointDate` and `selectedChartSeriesName`. `selectedSeries` resolves by display name, then `selectedChartPoint` uses `lastOrNull { it.date == date }`. `buildExerciseGraph` deliberately returns distinct per-session points for Workout aggregation, even when two workouts share a local date. Tapping the earlier point can therefore show the later point's value and open the wrong source workout. Two different Exercises with identical names can similarly collide in comparison selection. The previous native drill-down fixture has one Exercise and one workout; it cannot expose either ambiguity.

**Plan:** retain chart selection with stable series identity plus exact point identity (source session for Workout; date/bucket for aggregate points). Pass those identities through the existing `GymChartSeries`/chart callback seam rather than parse display text. Keep date/name labels human-readable. Store enough identity to reconcile recreation and cleared/recomputed series safely; a vanished source closes or invalidates the detail instead of silently selecting a neighbor. Do not change graph aggregation, eligibility, persisted records or source session IDs.

**Acceptance:** two same-day workouts with distinct values each open their own detail and History; same-named comparison Exercises resolve their own series; Week/Month aggregate details still have no fabricated single-workout action; selection restoration cannot cross to a different point. Use real visible point taps and the actual History callback, preserving the earlier chart gesture fix. Add exact identity helper tests only where they verify these collisions, plus one native multi-point source journey.

**Owner:** `GymScreens.kt`; focused `GymPowerInputUiTest.kt` or `CoreFeatureJourneyE2ETest.kt`, and existing `GymProgressScopeTest.kt` if a small identity resolver is extracted. No domain schema change.

### G2-B — Prescribe the exercise's actual measurements

**Source-confirmed mismatch and grounded authoring improvement, P1/P2.** `RoutineSetEditorCard` shows Reps min/max for every tracking type except WeightOnly, DistanceOnly and DurationOnly. That incorrectly includes DistanceDuration and WeightDuration; `ExerciseTrackingType.supportsRepetitionEntry()` explicitly excludes both, and the active Set editor already follows the correct policy. The new collapsed Set summary uses `routineSetSummary` plus load/rest/note, omitting distance and duration. Two running intervals with different distances/times can collapse to indistinguishable rows. The visible strength-only baseline does not validate the other nine tracking types.

**Plan:** use the established tracking capabilities for applicable inputs; preserve existing draft/persisted compatibility values instead of silently rewriting historical data. Build the collapsed prescription from applicable authored load, repetitions/range, distance/unit and duration, with concise rest/effort/tempo/note context when present. Do not make every row a full editor again. Retain selected Set, add/duplicate selection, phase scope, min/max validation and exact Save ownership. Inspect negative/invalid optional distance/load and duration inputs against the existing routine-to-draft validator; any added validation must match the repository contract and must not prohibit intentionally incomplete prescriptions.

The adjacent `ExerciseActionsDialog` has the same policy drift: weight defaults are gated by case-sensitive `trackingType.name.contains("Weight")`, which excludes BodyweightReps and AssistedBodyweightReps even though the library and editor correctly expose their load increments. Load meaning is shown unconditionally, including distance-only and duration-only Exercises. Include these inspector facts in the same capability-alignment change; the shared inspector shell remains untouched.

**Acceptance:** a parameterized capabilities check covers all tracking types; native DistanceDuration and WeightDuration editors omit Reps; RepsDuration retains Reps; two different timed/distance Sets are distinguishable while collapsed; values survive selection changes, recreation and save/reopen. Bodyweight inspector defaults agree with the library/editor, while duration-only details omit irrelevant load facts. Existing strength/percentage/numbered-machine, warm-up generation, multi-day and legacy phase fixtures remain neighbors.

**Owner:** `RoutineBuilder.kt` and Exercise inspector content in `GymScreens.kt`, minimal existing-domain helper reuse; `RoutineBuilderUiTest.kt`, `RoutineBuilderStateTest.kt`, `GymPowerInputUiTest.kt`, and relevant authored continuity journey.

### G2-C — Tell the truth about Rest alerts and verify permission return

**Source-confirmed delivery discrepancy, P2; lifecycle return remains untested.** `restTimerNotificationsAvailable()` checks application notification enablement and Android runtime permission only. It never checks the selected Rest channel (`RestTimerNotifications.channelId(timerSound, timerVibration)`). `SettingsContent` does check that channel's importance. A user can block that channel while allowing Whip notifications, leaving the running workout without its background-alert warning. The native 200% fixture denied the whole permission; it did not cover per-channel blocking.

**Plan:** resolve Rest availability from the same effective channel and notification rules used in Settings, retaining the in-app timer. A not-yet-created channel is not the same as a blocked channel. Preserve the compact persistent status and scrollable explanation at enlarged text. Add an actionable route only through an existing Settings/Android channel intent owner if useful; do not add a separate permission framework. Exercise the already implemented `LifecycleResumeEffect` with a real Android Settings excursion and changed delivery state, rather than count an Activity-only recompose as OS-return proof.

**Acceptance:** allowed app/permission + blocked current Rest channel shows the warning; allowed different channel does not override it; normal/uncreated channel and pre-33 permission behavior remain valid; timer and Save remain usable at native 200%. For return, open the real Android notification settings from Whip, change or arrange a deterministic test-only permission/channel state while Whip is backgrounded, return without pressing Refresh, and assert the updated status. Restore original emulator state in teardown. If OS automation cannot safely establish a state, report the exact limit rather than claim a pass.

**Owner:** `GymScreens.kt`, `SettingsScreens.kt` only if the reproduction finds a missing callback; existing notification policy helper may be reused. `GymPowerInputUiTest.kt`, `SettingsBehaviorUiTest.kt`, or a dedicated narrow permission-return fixture. Parent executes OS/device operations.

### G2-D — Make encrypted-backup entry usable and correctly classified as secret input

**Source-confirmed input configuration gap, P2.** Export and unlock fields use `PasswordVisualTransformation` but default `KeyboardOptions`; they do not request a password IME input type. Export mismatch marks only the confirmation border while Choose Location is disabled. The existing first-field explanation states eight characters, but there is no local mismatch reason or deliberate Next/Done flow. This is not evidence that an IME actually stored or disclosed a secret.

**Plan:** explicitly request password keyboard input and disable autocorrection/suggestions using supported Compose options; preserve masking and transient `remember` secret state, and retain fail-closed process-loss behavior. Add concise field-local mismatch/length explanation at a reasonable interaction boundary and usable IME traversal/submission. Optional reveal, if implemented, must be explicit, accessible, reset to hidden, and never expose secrets in logs/screenshots or saveable state. Prefer no extra reveal UI if keyboard and explanatory changes solve the demonstrated friction.

**Acceptance:** short/mismatched export input cannot launch DocumentsUI and explains why; matching valid input launches once; unlock failure remains local and retryable; real keyboard Next/Done remains reachable at compact native200; recreation does not restore plaintext passphrases; encrypted export during provider recreation retains its existing safe ViewModel request. Inspect native input type with synthetic test-only strings; no screenshot or log captures actual owner secrets.

**Owner:** `SettingsScreens.kt`; existing `DataPrivacyJourneyE2ETest.kt` and `SettingsResponsiveUiTest.kt`. No encryption, minimum-length, file format or document-request ownership change.

### G2-F — Resolve the machine-library search question with a real collection

**Confirmed absent capability; workflow cost still needs measured evidence, P2.** `MachineLibraryContent` presents a header, archive toggle, then every profile in `gym-machine-library-list`; it has no query or scope summary. Profiles carry name, location, configuration version and several linked Exercises. Reused versioned equipment can make a scrolling-only collection materially harder to navigate. This is distinct from Exercise search (already indexes all machine exercise links) and the workout machine-choice dialog (selection must remain exact). The prior audit's one/two-machine screenshots do not justify a claim of large-library friction.

**Plan:** seed 30 plausible synthetic profiles across locations and versions, with multi-exercise links; capture initial and the named distant target at ordinary width and large text. Count required list navigation, not an invented time saving. If the populated flow confirms costly lookup, add local `WhipSearchField` over profile name/location/version display and linked exercise names, with explicit clear-query/no-match recovery and unchanged active/archive scope. Reuse `rememberSaveable` query and existing matching conventions; no indexing service or new persistence. Check the machine-choice dialog separately before deciding whether the same local query is useful there.

**Acceptance:** exact intended version selected; secondary linked Exercise search works; archived collection does not leak active profiles; zero-match recovery clears only the query; query/scope survive recreation; archive/create/version/copy history behavior is unchanged. If the evidence does not warrant search, record keep with captures rather than silently call the proposal implemented.

**Owner:** `GymScreens.kt`; `GymLibraryJourneyE2ETest.kt`, narrow query JVM helper test only if matching is extracted. Parent executes reproduction.

### G2-G — Make deep Settings operations visibly settle

**Source-confirmed location; usability consequence needs native reproduction, P2.** General `state.busy`, `state.message` and typed warning cards are the first lazy items in `settings-list`. CSV/backup actions can be far down the Data & Privacy page, and there is no explicit reveal of those general results. After a failed provider/write operation, the user may remain at the initiating action while the result is uncomposed above the viewport. Existing backup tests usually scroll directly to an expected status and therefore do not prove discoverability without knowing its location.

**Plan:** reproduce a failed and successful deep CSV/backup action while keeping the actual scroll position. If the result is hidden, reveal the owned general operation result through the existing list/state owner, scoped to explicit Data & Privacy operations and excluding active restore/unlock/reset dialogs which already own their errors. Do not duplicate the same result in two surfaces or classify operation types by message text. A bounded reveal/scroll at the operation transition may be sufficient; avoid another permanent sticky card that consumes the native200 viewport.

**Acceptance:** after initiating a deep operation, visible working/result/error context is reachable without hunting; busy exports cannot launch another provider; success never precedes durable operation completion; dialog-local errors remain local; typed editor input and section navigation are not unexpectedly moved by unrelated background events. Capture before settling and after failure/success.

**Owner:** `SettingsScreens.kt`, existing `SettingsViewModel` only if structured owner metadata is actually needed; `SettingsResponsiveUiTest.kt` plus `DataPrivacyJourneyE2ETest.kt` neighbor. Prefer existing OperationStatus over new operation architecture.
