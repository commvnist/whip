## Accepted remedies

### DGS-1 — Make the whole workout navigable while logging

**P1 workflow redesign.** Current source: `WorkoutContent` selects one `nextSet`; only `WorkoutExerciseCard`'s `set.id == nextSetId` branch renders `QuickSetEntry`. Tapping every other incomplete Set invokes `onEditSet`, a full editor with classification, Planned, Completed, effort, tempo, rest and note controls. `requestedExecutionExerciseId` already supports exact incoming placement routes, but there is no ordinary in-session chooser. A user moving to another station must scroll through preceding exercises and use the full editor, or arrange the workout simply to make a different logger current. This is a poor everyday path even though both commands persist correctly.

The same card computes `hasIncompleteSet` and displays all completed Sets whenever it becomes false. Finishing the last Set of each exercise therefore re-expands its entire completed history. The sole Finish owner is the last LazyColumn item after all blocks, alongside Group and Discard. A six-exercise/four-set session can end with 24 expanded records between the user and that action. At 200% text, the sticky lane even drops the exercise name from its visual label, leaving only “NEXT · Set N” while the full identity scrolls away.

**Before → after:** retain the existing scrollable Set cards and rest timer, but add a compact workout overview/chooser to the existing execution lane. It names the current exercise and completed/remaining work and opens a bounded, scrollable list of the session's exercises, their progress, group context and exact next eligible Set. Choosing a station establishes an explicit quick-logging target and brings its existing composer into view. “Follow workout order” clears the choice. Completed Sets remain behind their disclosure even when that exercise is complete; their count and correction access remain visible. Finish is reachable from the overview without scrolling the complete session and reuses the same finish review callback. Group/arrange/discard remain deliberate management actions rather than peers competing with every repetition.

After a successful owned `WorkoutFinished` receipt, open that exact finished History record (the receipt already has `targetId`) so the person sees what was saved and can share, repeat or inspect it. Currently the receipt only closes the review and the session disappears into the generic launchpad. Failure must retain the review/active session. No new success dialog, second finish state machine or rewritten history.

**Effort:** station switching becomes overview → chosen exercise (two actions with a stable list), then the same quick Complete action; it no longer requires hunting through full Set cards or the Completed toggle. Finish becomes overview → Finish regardless of session length. Correction remains expand completed → exact Set, with no forced full-session expansion. These are structural counts, not measured seconds.

**Compatibility:** explicit choice is one saveable Set override, cleared when that Set completes so the next queued Set/group rotation resumes. It must never accept/skip an optional Joker implicitly, bypass required-work finish review, reorder stored exercises, or persist a new plan. Switching away must preserve unsaved quick drafts by Set identity; activity recreation must preserve the explicit selection and current draft. A removed/replaced/completed target must fall back safely. Rest keeps the existing deadline/revision owner: navigation alone does not cancel rest, completion uses its existing replacement policy, and finish runs existing persisted timer cleanup. Display full exercise identity at large text with bounded wrapping rather than removing it.

**Smallest acceptance:** one pure selection method covers grouped/ordinary/optional/removed targets; one real six-exercise journey chooses a later station, logs two Sets, switches away/back with an unsaved draft, recreates, corrects a completed Set, and finishes to exact History. One focused actual-200% short-height image verifies chooser and logger identity/action bounds. If the combined journey exceeds 55 seconds, split logging/navigation and finish rather than weakening assertions.

### DGS-2 — Make repeated-set suggestions and inputs preserve measurement meaning

**P1 correctness plus repeated-input clarity.** `QuickSetEntry.applySuggestion` copies `suggestion.enteredWeight` and `enteredDistance` directly while the receiving draft retains the current Set's unit IDs. A prior 100 lb entry offered to a kg Set becomes 100 kg. The distance field label uses `preferredDistanceUnitId`, although its saved draft uses `set.enteredDistanceUnitId ?: preferredDistanceUnitId`; changing the preference can therefore label a retained mile value as kilometres. The button's summary is also formatted through the current placement snapshot. `buildGymUiState` filters previous placements only by exercise and equipment scope, so free-weight interpretation changes (total ↔ per hand) can cross that boundary. `summarizePreviousSets` includes uncompleted Sets and the suggestion fallback picks the latest timestamp from that bounded list, allowing unperformed planned work to masquerade as previous performance.

The optional RPE/RIR input appears **after** Complete Set; the existing input-order test checks only load/repetitions. A user can naturally press Complete without ever seeing the effort field they deliberately enabled. Bodyweight lacks a unit label, and bodyweight visibility tests the current Exercise type while validation uses its immutable workout snapshot.

The connected Set Details route also drops context: `onMoreDetails` passes no draft, so a just-typed quick value is absent from the full editor initialized from the stored Set. After owned `SetUpdated`, only the modal's `editedSetId`/boundary are cleared; the quick form and authorship boundary remain saved under the unchanged Set ID. Returning to Complete can retain the old values and reject the stale boundary. This needs an owned handoff/refresh, not silently resetting drafts on every unrelated state emission.

**Before → after:** only offer completed, nonremoved, semantically compatible previous performance. Convert raw entered quantities from their actual saved units into the receiving entry units; do not substitute total effective resistance for a per-hand/per-side entry. Keep machine levels ordinal and partitioned. Use the receiving saved units in labels and snapshot tracking capability for all fields. Put enabled effort input before Complete Set, alongside the other applicable inputs; keep optional meaning explicit. Preserve explicit “Use Previous” rather than silently overwriting authored targets or current drafts. Set Details receives the quick draft; cancel retains it, and matching owned save refreshes that Set's quick values and boundary. External conflicting changes still require review rather than erasing a local draft.

**Effort/impact:** repeated Sets still use one suggestion tap, but the tap applies what its label promises. Enabled inputs are seen before submission; users need fewer historical corrections to add missed effort. No change to recorded historical values or formula policy.

**Smallest acceptance:** one pure cross-unit/snapshot suggestion method covers lb→kg, mile→km, per-hand compatibility, changed interpretation rejection, machine level and incomplete/omitted records. One exact native method applies previous values, changes preferences while a saved-unit Set is open, checks labels and final draft, and verifies enabled effort is before Complete at enlarged text. A focused correction method types a quick draft, visits/cancels Details, then saves Details and completes without stale rejection; external stale edits still fail locally. No real lifting recommendation is introduced.

### DGS-3 — Put essential exercise setup before optional library metadata

**P1 authoring hierarchy.** In `ExerciseEditorDialog`, Name and Tracking Type are followed by Notes and **every** category row. Only after that unbounded category list does “Advanced options” reveal kg/lb and “What one weight entry means.” These are essential choices for a dumbbell, plate-loaded bar or assisted movement: the same typed 20 means different performed work under total versus per-hand/per-side. A mature 30-category library adds at least 30 touch rows before the essential control can even be discovered. The prior keep treated the existence of snapshot validation as sufficient.

**Before → after:** basic setup is Name → what is tracked → applicable unit/load meaning/bodyweight rule, with the existing consequence and meaning-change review. Common unit/meaning choices are explicit on the normal path. Notes/cues stay available. Category assignment becomes a concise selected-count/name summary opening a searchable multi-choice surface with retained draft selection, so its height is bounded regardless of library size. Increment, plate calculator setup, formulas, display overrides and statistical inclusion remain the clearly named optional configuration group. Power mode changes initial disclosure only, never hides essentials.

**Effort:** a new dumbbell exercise no longer requires opening Advanced and scrolling past all categories to specify “per hand.” Selecting one category becomes open → search → check → done instead of scanning the entire category library. No auto-inference from the exercise name, no template that overwrites units, no rewritten history.

**Owner/reuse:** `ExerciseEditorDialog` is already used by library, workout and routine creation; change it once. Reuse established search, choice-row and dialog controls. A new generic form engine or cross-domain category abstraction has no demonstrated need.

**Smallest acceptance:** one exact native fixture with 30 categories creates a per-hand lb exercise, finds/selects two distant categories, preserves selection/draft through recreation, validates Cancel/discard, and confirms a duration-only type hides irrelevant load controls. Capture normal and native-200% basic setup; confirm no Save/body overlap with IME.
