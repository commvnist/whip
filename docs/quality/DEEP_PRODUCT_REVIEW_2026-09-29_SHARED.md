# Shared app and Task review — 2026-09-29

Status: In progress. FB-20260929-002 / FND-20260929-003. Baseline 0.3.83, `04bc58e2`. This is an assessment of complete jobs, not a screen count. The initial fresh Home capture uses synthetic sparse data; dense/changed journeys are separate forthcoming evidence. Source traces are current, but source inspection does not prove rendered quality.

## Job: decide what to do across a busy day

Home already has useful due counts, a true first-use/clear-day distinction, direct controls and authored section order. Its failure is scale: `HomeContent` emits every due Task and Habit, all pinned Tracks/routines and all pinned Goals. One domain can consume the entire feed. The fresh sparse original demonstrates the visual hierarchy but cannot excuse what its unbounded source does with twenty Tasks. DS1 therefore uses the same record cards with three-item previews, pins first and explicit total/continuation. No new aggregate score, automatic reprioritization, card style or collapsed-by-default whole domain is justified. Completing work refills the preview. Expanded finished Habits remain discoverable with their own continuation. Saved filter chips form one scrollable row; routine day choices likewise stop forcing unbounded vertical layout.

The continuation must route to the right collection, not whatever subdestination was used last. Home Tasks restores the applicable saved Home filter into Today without changing current Area; Habits targets Today, Goals Active, Tracks its collection, and routine continuation its routine collection. Counts stay source-derived. Distinguish a bounded preview from deletion or lost pins: pinned ordering is retained, and View All is explicit.

## Job: find, execute and correct several Tasks

`TaskAreaContent`'s search exists only inside a filter dialog; a person who wants one named Task must first discover a generic filter icon. DS2 exposes Find Tasks, uses the existing shared query control and matching owner, hides the competing quick-capture field while searching, and shows current scope/count. Query changes reset to the result header; unchanged restoration must retain context. Full-list reorder still requires explicitly clearing constraints. Saved-filter naming now retains the parent's state/scroll on Save and Cancel.

`TaskActionsDialog`'s Overview describes context first while execution controls are elsewhere. DS3 places actual subtasks first, makes Focus presets available directly, and places the schedule action with its timing fact. Activity remains useful for recurring history; Options holds organization/lifecycle. This preserves the domain distinction between moving one occurrence, changing future definition and editing a closed series. A new generic date editor or merged lifecycle command would obscure that meaning.

Following the edit path exposed a related continuity problem: the shell clears the active inspector before opening its definition editor. DS3 keeps the existing inspector mounted behind the child, renders the child last, and dismisses only the child on save/cancel. Pin updates also retain the inspector. Focus child dialogs retain the inspector's scroll owner. Duplicate, completion and whole-entity removal still follow the existing intentional transitions; a disappeared source cannot remain editable.

## Job: understand progress, inspect its evidence, return and compare

`ReviewDialog` exposes actual dated source outcomes and Area-aware summaries. Its scoring stays distinct from raw entries and may intentionally bound Goal scores. `ReviewAppRoute`, however, closes Review when opening any original record. DS4 stores the existing Review subtree and exposes Return to Review in the source workspace; Back returns after the source child's own Back behavior. Selection, period and list context survive recreation. No duplicated embedded editor or invisible modal layer is introduced. The root destination handler must yield to the return path once children are dismissed.

The same review was keyed on entire Goal/Gym states despite their clock-only updates. Its persisted evidence key now contains only completed/archived Task facts and occurrences; Habit definitions/logs/pauses/skips/units; Goal definitions/entries/milestones; and finished-workout source rows. Date, zone and ready sections remain independent cache inputs. Signals and correlations reuse those outcomes. This is a precise work-avoidance claim, not a measured rendering-speed claim.

## Reuse and extensibility decisions

Reuse `WhipSearchField`, record cards, inspector groups, lazy lists, existing menu/action/selection patterns and request coordinators. New `HomePreviewContinuation` serves all truncated Home domains; `ReviewSession` owns Review's saved inspection loop; `HomeHabitValueEditor` owns Home's additive/replacement dialog request. The root routes between existing domains instead of owning their new state details. Habit numeric actions/evidence, bounded exercise category selection, Track analytical scope and exact previous-set conversion similarly have one owner across their callers. Do not introduce a cross-domain schema/form engine or general chart API: units, event meanings and lifecycle policies differ.

The first Android package proved an actual architecture limit: JaCoCo reported `MethodTooLargeException` for `WhipScreen`. Feature ownership extraction is therefore a concrete build/extensibility repair, not cosmetic file shuffling. The repaired package's instrumentation task passes with coverage still enabled; complete packaging and native acceptance are recorded separately.

All DS1–4 remedies and the documented follow-through are accepted in the central plan and are being implemented. No claim that this finite review proves the absence of all bugs or subjective perfection is made. Final evidence must distinguish retained source dispositions, executed behavior and personally inspected current originals.
