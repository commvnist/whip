# Deep Habit, Goal and Track review — 2026-09-29

Status: **Proposed, awaiting parent reconciliation; no production edits.** FB-20260929-002, clean baseline `04bc58e2`, private 0.3.83/code 89. Parent owns shared integration, canonical memory and serialized verification. This report challenges the previous review's keeps using current source and complete user jobs. Interaction counts below are source-derived control steps, not measured device timings. Prior screenshots are clues, not fresh rendering evidence.

The main problem is inconsistent access to an entity's work. Opening a Habit can remove the numeric controls available on its collection card; Goal completion-based logging asks for a meaningless number; Track analysis loses its filter context when the user goes to inspect the underlying records. Mature collections and milestone forms then amplify these gaps through scrolling. The proposals below address those connected jobs rather than declaring every existing screen adequate because it has controls.

## DP1 — Habit details should support doing and reviewing the Habit

**Before / source.** `HabitProgressCard` (`HabitScreens.kt:1050–1290`) exposes configured Count/Decimal quick values, decrement, Set and Undo inside its expanded content. The only Today inspector callback is `onQuick` (`HabitAreaContent:493–568`, `HabitActionsDialog:2989`), so opening the same entity from Home/search/Insights removes these controls. An arbitrary additive amount is reachable through History → Add an Earlier Entry even for today's fact; Set Total requires leaving details and finding/expanding the collection card. `HabitValueDialog:2749` correctly explains replacement total, while `HabitHistoryLogDialog:2847` is the existing additive fact editor. This is an access problem, not a reason to invent new arithmetic.

The Today body puts streak and 30-day metrics before checklist execution. The prior large-font capture required scrolling past this summary to reach the newly added checklist. Meanwhile `HabitInsights:1619` owns the actual eight-week chart and activity grid only in the workspace's long list of every Habit. `HabitDetailSection:3458` has Today/History/Options; a person investigating one Habit has to dismiss details, navigate Insights and scan the collection again. The previous blanket keep of Habit Insights overlooked this detour.

**After / scope.** Make Today execution-first: concise current state, checklist or shared numeric action panel, then secondary schedule actions. Extract the existing Count/Decimal actions for reuse in cards and details; name Set Total explicitly, add an additive Add Amount child form using the existing history mutation path with today's initial date, retain configured quick values and exact Undo. A focused Insights section shares the existing chart/evidence body with workspace Insights, keeping low-pressure, flexible-period and original-unit meaning. Move historical metrics out of the primary work area; do not add a second analytics implementation. Preserve parent context through every child save/cancel/failure. Existing pause/skip/linked/read-only gates apply in both callers.

**Effort change.** From an open inspector, setting a total currently needs Close → find/expand card → Set → Save (plus input); it becomes Set Total → Save. An arbitrary amount no longer requires navigating to a tab labeled History and a control labeled Earlier. Reviewing the current Habit's pattern becomes one section selection, not exit → Insights → search/scroll.

**Owners / risk.** HabitScreens, HabitViewModel's existing `log`, `setPeriodValue`, `undoLog`/request coordinator. Home calls `HabitProgressCard` at WhipApp:5247/5267/5292, so shared numeric controls must preserve those callbacks/defaults; parent owns any required integration. Risks are additive-versus-replacement confusion, undo ownership, bypassing unavailable states, and four-tab layout at large font. No new persisted field or daily-score semantics.

**Smallest acceptance.** One exact native numeric journey: custom unit, nondefault quick amount, add arbitrary amount, set total, undo, local child failure/cancel and recreation; verify original individual facts and parent retention. One focused constrained capture of checklist/numeric Today and focused Insights. Reuse existing domain arithmetic tests; add only a needed pure action-availability contract if branching changes.

## DP2 — Record completions in completion-based Goals

**Before / source.** `GoalMeasurementDialog:2239` always requires a numeric field. `measurementEntryInstruction:3135` says any positive value records one completion, zero does not count; label is Completion Value. `calculateConsistencyProgress` (`GoalModels.kt:900–946`) counts positive entries, not the number entered. Thus typing 5 appears quantitative but records exactly one completion. Both new and edit routes (`GoalScreens:721/743`) share the dialog; current card/inspector action language is generic Log Progress.

**After / scope.** For CompletionCount, a new entry is an explicit Record Completion with date and optional note, requiring no artificial numeric keyboard step. Existing records show whether they count as a completion and offer a deliberate outcome change. Unrelated note/date edits retain the exact original value (including legacy 5, zero or negative), rather than silently rewriting it to 1. A user changing outcome deliberately writes 1/0. Apply accurate action/title/history wording to CompletionCount callers while retaining ordinary numeric logging for Sum/Latest/Average/etc. Never change Goal lifecycle automatically.

**Effort change.** New completion currently requires Log Progress → numeric field → type an arbitrary positive value → submit. It becomes open Record Completion → submit, with date/note only when wanted. The number of recorded completions and meaning become explicit.

**Owners / risk.** GoalScreens presentation and existing GoalViewModel recorded/update request boundaries; GoalModels rules remain unchanged. `GoalMeasurementDialog` also serves direct Home/global routes, so changing its shared owner covers them. History search must still match original numeric facts. Preserve zero/nonstandard originals and out-of-window review. Never conflate a completion event with Complete Goal.

**Smallest acceptance.** Exact JVM presentation/retained-value mapping covering new1, unchanged5/0, explicit outcome toggle; one native Consistency journey records a completion without numeric input, corrects its note/date and verifies progress remains one event plus unchanged nonstandard originals.

## DP3 — Find entities inside mature collections

**Before / source.** HabitList (`HabitScreens:1399`), ArchivedHabitList (`1869`), HabitInsights (`1619`), GoalAreaContent's Active/History/Archived lists (`GoalScreens:405–505`), GoalInsightsContent (`1242`) and AllTracksPage (`TrackScreens:1316`) have no local entity query. Existing History search only finds records after opening an entity; Track Entries search likewise searches inside one Track. Global search can find an entity, but it replaces the collection task and does not narrow the list used for repeated management. This matters when returning to several similarly named or archived items; previous “reorder/archive collections keep” did not examine locating them first.

**After / scope.** Provide consistent local Find Habits/Goals/Tracks over entity name, notes/description, tags and relevant type/status labels. Keep each destination's meaning and Area scope, show result counts and a clear recovery, retain query through details/recreation, and include matches currently under Finished Today. On Insights lists, query narrows cards before expensive visible-row analysis. Reorder requires clearing the query so a filtered subset cannot overwrite saved order. Track selection is bounded to displayed matches and revalidated before mutation; do not leave hidden selected rows targeted after a query change.

**Effort change.** A mature list currently takes an unbounded number of swipes per item or repeated global search/return. Local query narrows the actual workspace once and supports repeated open/correct/restore/return jobs. This is entity discovery, distinct from the previously implemented single-entity event search.

**Owners / risk.** Feature list owners; shared WhipSearchField and existing query normalization, with prepared entity search strings remembered on content changes. Do not introduce another full-text database or generic filter framework. Main risks: false first-use/empty state, hiding Finished matches, filtered reorder loss, selection leaking across scopes and expensive rebuilding per keystroke. Archived entity contents stay intact; no bulk destructive action is added.

**Smallest acceptance.** Exact pure matching tests across names/tags/types; bounded native mature-collection journey with ordinary/Finished/archive matches, clear, retained query after child return/recreation, and filtered reorder/Track selection safety. Request fresh dense-list captures, not a new hundreds-state catalog.

Keyboard/list contract: use WhipSearchField; input remains reachable while results change. A changed query starts at its result header rather than retaining an out-of-range prior index; opening a result dismisses the IME and returning restores the query/result context. Back first dismisses the keyboard through existing ownership, not the workspace. Clear preserves the destination/Area. Entering reorder with an active query offers Clear Search & Reorder explicitly; no implicit partial reorder. Track selection changes are applied only after displayed-ID reconciliation.

## DP4 — Milestone authoring should scale beyond a few items

**Before / source.** GoalEditorDialog (`GoalScreens:2035–2138`) renders every milestone as a full Card containing a numbered header, reorder/delete controls, a second numbered name field, Weight and Reward fields. This makes optional weight/reward configuration dominate a simple equal-weight checklist. Fifteen milestones mean 45 text/number fields before reaching Schedule/Organization, even when all weights are 1 and every reward is empty. The prior review kept this authoring layout solely because its saved identities and validation were correct.

**After / scope.** Compact milestone rows around the name, reorder and removal, with an explicit Weight & Reward disclosure and concise current summary. Default equal-weight items do not expose two unnecessary editors. Nondefault weight/reward remains visible in the summary; editing retains exact raw values and validation opens the affected details automatically. Use stable milestone IDs/UUIDs for disclosure identity and preserve draft/reorder behavior. No separate nested editor or replacement of the shared reorder owner.

**Effort change.** A simple 15-item plan presents 15 name inputs instead of 45 full inputs. Optional settings remain one action away. The reduced number of visible controls and repeated headings is structural; actual saved pixel/scroll distance must come from fresh captures.

**Owners / risk.** GoalEditorDialog only plus exact editor fixture. Risks: hiding invalid raw weights or custom rewards, disclosure state following row indices after reorder and losing an edited draft on collapse/recreation. Completion and weighted projection remain unchanged.

**Smallest acceptance.** Exact native create/edit with multiple equal-weight rows, one custom weight/reward, reorder, invalid weight auto-reveal, recreation and save; verify weighted outcome and original milestone identities. Fresh normal/large-font long-form capture.

## DP5 — Track analysis needs an explicit scope and a route to its evidence

**Before / source.** TrackInsightsPage (`TrackScreens:2319`) exposes All Entries counts and per-field statistics, but answering “what happened in the last month?” requires Filter Insights → Add Condition → Entry Date/operator/date inputs → Add → Apply. Its `conditions` and `conditionMode` are owned independently from TrackEntriesPage (`1850`), so switching to Entries silently loses the analytical slice. A suspicious average cannot lead to its matching records without reconstructing filters. Numeric/scale “trend” is only first-to-latest difference plus static facts; a spike then return is invisible despite materially different recorded data. Field aggregation is already unit-aware through TrackInsightNumberFormat; reuse it.

**After / scope.** Keep one explicit detail-level analysis/date scope across Entries and Insights, including existing typed conditions. Add common 7/30/90-day and All dates choices, show the actual inclusive range and entry count, and allow the existing detailed filter editor for custom scope. View Matching Entries navigates to the same filtered records, preserving a route back after correction. Add a compact date-spaced numeric/scale trend with visible range/unit/date labels and an accessible original-value data disclosure; repeated dates remain separate observations and missing values are not fabricated. Empty/sparse/future-date scope is truthful. No new forecast or aggregation semantics.

**Effort change.** A recent-period review becomes one range choice; inspect/correct the matching evidence becomes one navigation action instead of rebuilding a compound filter. A plot exposes temporal shape that equal first/last values conceal.

**Owners / risk.** TrackDetailPage/detail state, TrackEntriesPage, TrackInsightsPage, existing condition saver and TrackInsightNumberFormat. An extracted small chart renderer is reasonable only if it preserves Goal semantics and parent agrees shared ownership; otherwise keep Track-specific data formatting and rendering. Do not invent a cross-domain chart framework. Risks: query-versus-filter ambiguity, EntryDate versus authored Date-field confusion, inclusive/future date rules, units/offset conversions, paging invalidation, recreation and linking the right evidence. Existing Entry search remains visibly separate from analytical filters.

Date truth: `TrackEntry.entryDate` and `TrackEntryDraft.entryDate` (`TrackModels:105/154`) are nonnullable LocalDate, distinct from optional custom Date-field values. Scope uses Entry Date and the `today` already supplied by Whip's calendar owner, not the device's unrelated wall-clock zone. Last N days means `[today-(N-1), today]` inclusive and excludes permitted future Entries; All Dates includes them. Range is ANDed with the existing Match All/Match Any condition group, so a recent range cannot accidentally become an OR condition. View Matching Entries explicitly clears an unrelated old text query while retaining this exact range/condition scope; the destination shows that scope and count. Ordinary tab switching retains each view's state. No new persisted preference or timestamp conversion.

**Smallest acceptance.** Pure date-scope/plot-value checks for boundary/future/sparse/mixed-original-unit values; one exact native recent-range → trend → matching Entry correction → return/recreation journey. Fresh ordinary and constrained Insights originals with uneven dates and a midseries spike. No blanket performance claim: prepare series per content/scope change and compose visible cards lazily.

## DP6 — Honor a Track author's chosen list details

**Before / source.** TrackFieldEditor (`TrackScreens:3726`) says Show Label in Entry List will show this field's name/value. TrackEntryRow (`2234`) silently takes only the first two `showInList` fields. The third configured field never appears and no remaining-count affordance explains why. Entry details still contains it, but the author has no feedback that their display option was ignored. This affects both detail Entries and workspace Activity because they share TrackEntryRow.

**After / scope.** Keep the compact first two facts and explicitly disclose the remaining configured details in the shared row (count + expand/collapse or a clearly labeled View All Details action consistent with shared record-row ownership). Respect authored field order, original units and blank values. The configuration text must describe the actual behavior. Avoid silently expanding all 20 possible fields in every list row.

**Owners / risk.** TrackEntryRow, TrackFieldEditor copy; any shared WhipRecordItem change belongs to parent and should be agreed first. Risks are row-click conflict, accessibility expansion state and scroll after a row's height changes. No storage change or new showInList setting.

**Smallest acceptance.** One focused native row with four configured fields proves all are discoverable in detail Entries and Activity, with retained date/identity and accessible action at large font. Exact original capture shows the count/disclosure and remaining labels.
