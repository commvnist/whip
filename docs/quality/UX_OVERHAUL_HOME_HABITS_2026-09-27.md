### FND-019: real note-only Habit persistence

The real-history Insights fixture exposed [FND-20260927-019](../product-memory/FINDINGS.md): both Add an Entry and historical editing offer an optional number, but `RoomHabitRepository.log`/`updateLog` unconditionally called the strict quantitative Measurement writer. A Recorded entry with no number failed with “A value is required.” Replacing the fixture with zero would have hidden the broken authoring flow and invented a quantitative fact, so the parent explicitly approved this narrow persistence repair under HT-05/06.

`HabitRepository.kt` now stores `LogOnly + Recorded + null value` directly as a real Habit log with nullable value, canonical value, entered unit and measurement link. Numeric-to-note editing deletes the old linked measurement; note-to-numeric editing creates it with the existing Habit log UUID as provenance. Both transitions remain within the existing Room transaction, preserve log identity/authored timestamp and use the requested effective date/note. Undo already supports an absent link. Other modes/statuses still use the strict Measurement validation; no schema or backup-format change is introduced.

Source review confirmed nullable fields in `HabitLogEntity`, optional-link validation in backup restore, null-preserving JSON/CSV export, and activity/outcome calculations that do not manufacture a numeric value or successful outcome from a note. Three new repository/backup methods below cover persistence/recreation, both transition directions, undo, validation rollback and full backup restore. The existing Insights fixture additionally authors the current note through the actual blank-amount UI. All these checks passed in Native4 batch 1, including the full Habit repository class and the existing comprehensive backup round-trip regression.
