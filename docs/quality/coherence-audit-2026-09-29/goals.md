## Prioritized findings

### G1 — P1 correctness: a valid reduction Goal can report reached before reaching its target

**Evidence: S plus D1 fresh parent-operated device reproduction, personally inspected PNG/XML.** `GoalScreens.kt:1923` calls the starting value optional for Reduce, and the built-in weight template at `1511–1525` creates ReduceValue with a target and no baseline. `GoalModels.kt:191–228` requires a finite target but never validates the direction of the baseline→target interval. `calculateGoalProgress` at `801–812` substitutes baseline `0.0`, then divides `(baseline-value)/(baseline-target)` for reduction. It is algebraically the same ratio as an increasing Goal when the interval is reversed.

Reproduction: Create Reduce a Value, target 80, leave Starting Value blank, save, log 90. The computed progress is `(0-90)/(0-80)=1.125`: **112.5%**, success-colored full bar, Target reached and Review/Complete opportunity (`GS:853–858,899–901,951–960`). Log 70 and progress instead becomes 87.5%, despite the reduction target being exceeded in the intended direction. The weight template reaches this state without advanced configuration. Similarly, Reach baseline 100/target 80 rewards movement downward despite its increasing direction.

Impact: target truth, completion prompting, frozen closure percentages, pace and normalized Review scoring can be wrong in an ordinary weight/debt flow. Existing `GoalRulesTest#increasingAndDecreasingProgressUseBaseline` and over-target tests supply a valid reducing baseline; they do not exercise omission or reversed intervals.

Concrete remedy: make the baseline contract explicit. Require and explain a starting value above the target for reduction percentage, or show direction-aware binary reached truth with percentage unavailable until a real baseline is authored. Never silently invent the first measurement as baseline or rewrite existing evidence. Validate incompatible baseline/target directions at the shared domain owner, with field-level explanation in the editor. Preserve intentionally supported equal-baseline binary behavior and >100% for sound intervals. A saved legacy invalid interval needs an honest display fallback/repair route, not a false completion cue. Verify target80 / baseline omitted / values90→70, sound100→80 / value70, equal endpoints, negative-valued increasing/reducing intervals, Home/Review/closure and the weight template.

### G2 — P2 correctness/coherence: Insights uses the physical date ahead of Whip's logical day

**Evidence: S, current end-date owner mismatch; fresh custom-cutoff reproduction requested.** `GoalViewModel.kt:185–197` projects current progress using `calendar.logicalDate`. `AppSettings.kt:158–169,463–475` deliberately makes the logical day yesterday before an authored day cutoff. However `GoalInsightsContent` at `GS:1324` and `GoalActionsDialog` at `GS:2629–2630` derive through from `nowMillis.atZone(zoneId).toLocalDate()`, bypassing that cutoff. Both then feed it into `buildGoalInsights`, which uses through to decide eligible recorded dates, excluded count and forecast expiry (`GM:615–626,666–674`).

Reproduction: Set Whip's day cutoff to 06:00; at 01:00 local time on September 29 use a Goal with September 28 and 29 observations (the latter could have been authored before the cutoff was changed or restored). Current projection is through September 28. The inspector/Insights trend includes September 29, so its last value/rate/excluded count can describe evidence not included in the current outcome. Even without a physical-day observation, a forecast landing on logical September 28 can be hidden as before physical September 29. This is distinct from the deliberate explanation that rolling charts show observed dates while current progress uses today's window.

Concrete remedy: pass the already authoritative `GoalUiState.currentDate` through collection Insights and inspector calls for measurement/consistency analytics and key their remembered results to it. Keep elapsed duration based on exact instants. Test before/at/after cutoff, date/zone changes without midnight, historical physical-day entries, windowed goals, consistency and forecast expiry. Do not add another clock calculation.

### G3 — P2 usability: type switching can strand an invalid field that is no longer visible

**Evidence: S, deterministic editor/validation trace; fresh device reproduction requested.** `GS:1694` always builds precision from raw text (`null→-1`). The type picker resets precision for Consistency/Elapsed (`1819,1827`) but WeightedMilestones (`1822`) changes only unit/dimension. Measurement and Decimal Places controls disappear for milestones (`2055–2110`), while `GM:198` always rejects precision outside 0..6. The Save handler reveals `advancedMeasurement` only for numeric types (`2268–2276`), so its validation summary cannot expose the missing field for correction.

Reproduction: New numeric Goal → Progress Calculation → Decimal Places blank or 7 → change Goal Type to Finish Milestones → supply a valid positive-weight named milestone → Save.
