## Prioritized findings

### SET-01 — P1: merge can report failure after importing the user's records

Source-confirmed failure boundary. `BR202–266` commits merged records in a database transaction, then `BR268–270` ensures the default Area and rebuilds search. `VM981–1005` additionally cancels notifications and invokes `WA607–623` background reconstruction before it reports success. Any index/provider/WorkManager/scheduler exception after the transaction reaches the same `OperationStatus.Failed` branch and `S1981–1987` renders **Import Not Completed**. The pending preview remains, even though records may already exist. Area mutation receipts already distinguish committed changes from follow-up warnings; merge is incoherent with that stronger neighboring contract.

Reproduction: import a valid backup containing new records; inject an error in post-commit Track search-index rebuilding or a reminder/background sync; observe imported records in storage while preview says import not completed. This is a source path, not an executed failure injection in this audit. Impact: the recovery user cannot tell whether anything changed, may distrust or repeat the import, and may unknowingly retain unscheduled reminders. Idempotent merge prevents ordinary duplication but does not make the displayed outcome truthful.

Remedy: return/preserve a committed merge receipt (imported/skipped counts) at the database commit boundary, finish post-commit repairs independently, clear the actionable import preview once import is committed, and report **Data imported; background/search refresh incomplete** with an owned repair retry. Catch only repair failures as warnings. Retain a real import failure and staged candidate when the transaction did not commit. This is feedback/lifecycle correction, not a new backup format or change to merge identity rules.

### SET-02 — P2: Organization drafts lack the dismissal protection used by adjacent Settings editors

Source-confirmed consistency defect. Create Area `AP242`, Rename Area `A973–995`, Create Tag `T441–495` and Rename Tag `T503–560` call their close handler directly from `onDismissRequest` when not saving. Drafts are saveable through recreation, but ordinary Android Back/outside dismissal removes the only live copy. Custom Unit `S2617–2620` and custom Emoji `S2100` ask Keep Editing/Discard for dirty drafts; they establish the surrounding product contract.

Reproduction: Settings → Organization → Manage Tags → Create Tag; type a name; press Android Back; reopen Create Tag. Repeat for Rename Area after typing a replacement. Impact: accidental dismissal loses authored naming work and makes analogous forms behave unpredictably. Explicitly submitted failures already preserve drafts correctly.

Remedy: share the existing dirty-dismiss guard for Area/Tag name and Area color drafts; compare normalized initial value and use Keep Editing/Discard on Back/outside. Preserve explicit Cancel behavior according to the established editor policy. Do not add confirmation to pristine forms or lifecycle-safe saves. Verify draft recreation plus dirty Back for one Area and one Tag journey. Actual keyboard/outside/touch behavior still requires new runtime evidence.

### SET-03 — P2: compact Area detail loses the manager's reading position

Source-confirmed state-owner defect. Compact `A274–296` replaces `AreaListContent` with detail. The list is composed only in the other branch and `A506–513` does not receive a host-owned state. Back clears `detailId` and recreates the list at its initial position. Query and archived disclosure remain saveable at the manager host, producing a retained filter with a lost viewport. Wide mode avoids this because the list remains mounted.

Reproduction: create enough Areas for several screens; scroll to the final Area; open it; Back to Areas. Impact: repeated comparison/editing forces rescrolling, disproportionately at 200% text. Remedy: retain list state in `AreaManagementDialog`, supply it to both compact and wide list instances, keep search's intentional reset separate, and preserve stable Area keys. Related detail-section and root Settings list fixes do not cover this owner. No fresh device reproduction was performed here.

### SET-05 — P2: equal quiet-hour endpoints advertise enabled protection with no effect

Source-confirmed semantic mismatch. `S1351` treats nonnull start/end as enabled and `S1382–1384` displays the selected pair. Both typed fields accept every valid clock independently. `core/QuietHours.kt15` explicitly returns the original instant when start equals end. Thus **Enable notification quiet hours** can be checked beside `22:00–22:00` while every reminder proceeds normally; no explanation names the zero-length policy.

Reproduction: enable quiet hours; set End to the same time as Start; save. Impact: someone relying on quiet hours believes protection is active. Remedy: explain **No quiet interval: choose different start and end times** adjacent to the pair and in the editor, or reject the equal pair with retained draft. Do not silently reinterpret it as all-day silence. Preserve legitimate daytime/overnight deferral and exact typed receipts. Weekend overrides are absent from this product contract and are not a required new capability.

### SET-06 — P2: several immediate Settings controls and Area follow-ups still have no durable failure feedback

Source-confirmed incomplete persistence contract, not a measured ordinary-use failure. Theme, dynamic colors, Home show/order, most Gym dropdowns/toggles and custom-emoji remove/reorder use `VM.update` (`S568–607`, `S696–738`, `S970–1047`, `S1118–1139`; `VM305–329`). This delegates to `AS297–299,379–381` `SharedPreferences.apply()`, reporting no disk result. The neighboring typed Number/Clock/Zone/custom-emoji authoring paths use `updateAndConfirm` and an exact receipt. In addition, `VM664`, `VM681–688`, `VM700` execute unconfirmed Area scope/opening/saved-view follow-ups; `areaFollowUpWarnings` only catches exceptions, so asynchronous storage failure cannot produce its stated warning.

Reproduction: fail preferences disk persistence after selecting a different Home section order or after merging the current/chosen Area; local state advertises success, then process restart restores old preference state. Existing typed-persistence tests have a relevant failure seam, but this audit did not inject it. Impact: apparent customization/scope changes can disappear after restart; a saved-with-warnings receipt can falsely omit a failed follow-up. The common emoji picker Save & Use is a separate parent-owned integration finding; this item is specifically the remaining Settings controls and Organization follow-up receipts.

Remedy: reuse the existing asynchronous confirmed setting mutation owner for user-authored controls, retaining immediate visual responsiveness if appropriate while surfacing failure/rollback and disabling only conflicting work. Use checked `updateAndConfirm` for Area follow-ups and publish the existing committed-success warning when that confirmation fails. Do not create a modal Save button for every switch or a second persistence framework. Retain simple reversible remove/reorder without destructive confirmations.

### SET-07 — P3: plain custom-unit Archive gives less consequence guidance than Create New Version

Confirmed discoverability gap, with sound underlying data safety. `S846–855` archives immediately without explanatory/undo copy; `S824–845` lists dimension/factor but no current usage. `MR417–425` only changes the unit's archive flag. The new-version dialog explicitly says current definitions/history keep the old contract and new pickers exclude it (`S2730–2736`), while plain Archive leaves that relationship implicit.

Reproduction: create a custom unit used by a Habit/Goal/Track Number field; Settings → Custom Units → Archive. Impact: the author cannot know from the manager whether the connected item will break or whether historical measurements change. Remedy: add concise persistent manager guidance that Archive removes the unit from new choices while existing uses/history remain valid, and pair the reversible action with Undo or nearby Restore. Add usage counts only if readily available from an existing projection; a new global usage-index subsystem is not warranted. Do not block archival of an in-use unit or edit its conversion meaning.

### SET-08 — P3: Settings search omits vocabulary for supported Organization operations

Source-confirmed search result gap. `SS60–62` entries include create/archive/rename for Areas/Tags and icons/identity for emojis, but omit **merge**, **move**, **color**, and emoji **rename**. `SS77–82` requires every query term to occur in the combined entry text. Consequently `merge tags`, `merge areas`, `move area` and `rename emoji` return no match despite supported actions in the launched managers.

Impact: purpose-based Settings search becomes least useful for infrequent/consequential organization work. Remedy: add action aliases to existing manager entries, landing on the existing Manage Areas/Tags/custom-emoji anchors. Keep the manager as the place for record selection; do not invent record-specific Settings search results or duplicate taxonomy search.
