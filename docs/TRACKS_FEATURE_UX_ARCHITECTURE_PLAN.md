# Whip Tracks feature, UX, design, and automation plan

Status: implemented technical architecture; automation UX terminology is superseded by the 2026-08-24 audit

Date: August 23, 2026

The persistence, identity, and reconciliation architecture in this document
remains valid. For current user-facing automation terminology, configuration
hierarchy, and acceptance criteria, use
[`AUTOMATION_UX_AUDIT_2026-08-24.md`](AUTOMATION_UX_AUDIT_2026-08-24.md).

## Outcome

Tracks are Whip's first-class structured logging domain. A Track
records facts; a Goal evaluates those facts; a Task represents an action; a
Habit represents repeated behavior. This separates evidence from ambition and
lets one body of evidence serve more than one Goal.

Examples:

- `Books Read` records title, author, genre, rating, and thoughts. `Read 50
  Books` counts every eligible entry; `Read 10 History Books` counts only
  entries whose genre is History.
- `Chess Openings Learned` records opening, side, variation, moves,
  confidence, and notes. `Learn 20 Chess Openings` counts entries; `Know 10
  Openings Confidently` counts entries whose confidence is at least 4.
- `Job Applications` records company, role, submission date, and result. A Goal
  can count submissions or the entries whose result is Interview.

The feature replaces the proposed Itemized Goal design. Entries belong to a
Track, never to a Goal. Goals consume Track events through Whip's existing
Link/Contribution model.

## Product ontology and vocabulary

| Concept | User-facing meaning |
| --- | --- |
| Track | A reusable structured log, such as Books Read |
| Field | One named piece of an Entry, such as Author or Confidence |
| Entry Identity Field | One of one or more required Fields combined into the Entry title |
| Entry | One dated fact recorded in a Track |
| Progress Automation | A rule that turns eligible Track Entries into Goal contributions |
| Capture Automation | A rule that prompts for a Track Entry after a Task or Habit event |
| Follow-up Automation | A rule that prompts a Task or Habit after a Track Entry |
| Contribution | Inspectable Goal evidence generated by a Progress Automation |

Use `Entry`, not `row`, `record`, or `database`, in the interface. Use
`Progress Automation`, not the ambiguous `Link Progress`, when an event changes
a Goal. Context-only relationships remain `Connections` and never change
progress.

Adding the Track noun makes the current Goal label `Track a Trend` ambiguous.
Rename that Goal type to `Observe a Trend` as part of the instructional audit.

## Product boundary

Tracks include:

- user-defined fields with no fixed field-count limit;
- typed entry forms, validation, search, filtering, sorting, and insights;
- one stable Area per Track and Track-level tags;
- archive, duplicate, export, backup, restore, and permanent deletion;
- Progress Automations into Goals;
- Capture and Follow-up Automations involving Tasks and Habits;
- stable source identity, backfill preview, contribution audit, exclusions, and
  overrides.

Tracks do not include:

- formulas or user-authored code;
- relationships between Entries or between Tracks;
- nested Entries, subtables, rollups, or lookups;
- arbitrary custom views, dashboards, or Kanban states;
- attachments in the first implementation;
- collaboration, cloud forms, or public databases;
- automatic AI classification or schema generation;
- planned/draft Entry states. A Track is evidence; planned work remains a Task.

The lack of a field-count limit must not imply an unbounded feature model. The
simple field types and non-relational Entry model are the boundary.

## Information architecture and navigation

Tracks must not be hidden in Settings or Workspace Tools. They also must not
become a sixth bottom-navigation item without redesigning all primary
navigation.

The first implementation uses four explicit entry points:

1. The global Add menu includes `Track`.
2. Home includes a `Pinned Tracks` section after the first Track is created.
3. Unified Search includes Tracks and Track Entries.
4. Goal, Task, and Habit Automation surfaces can choose or open a Track.

Home anatomy:

```text
Today
...

Pinned Tracks

Books Read                         Add Entry
12 Entries · Latest Aug 21

Chess Openings Learned             Add Entry
7 Entries · Latest Aug 20

All Tracks                                      >
```

`All Tracks` is a navigation row with a right chevron and the accessibility
label `Open All Tracks`; it must not look like a filter, disclosure, or action
button. If no Track exists, Home does not reserve a permanent empty section;
Track remains discoverable through global Add and Search.

The All Tracks page follows Whip's shared hierarchy:

```text
Tracks                                         Search  More
Structured logs that can support actions and Goals · 4

Pinned
...

All Tracks
...
```

- The contextual `+` creates one Track. Do not also place a permanent `Create
  Track` button beside it except in the empty state.
- Archive is a filter under More, not a permanent peer tab.
- Selection mode is entered through More or long press and uses the shared
  selection grammar.
- Area scope filters Tracks by their Track Area. Entries inherit their Track's
  Area and never store a competing Area.

## Track creation and field design

The editor uses Whip's causal order:

1. Identity.
2. Entry definition.
3. Organization.
4. Optional details.

```text
Create Track

Name *
[ Chess Openings Learned                        ]

Icon
[ current icon and picker                       ]

Entry Fields

Opening *                          Short Text · Primary
Side                              Single Choice
Variation                         Short Text
Moves                             Long Text
Confidence                        Scale 1-5
Notes                             Long Text

[ Add Field ]

Area
[ Main                                          v ]

Advanced Options
```

A blank Track begins with one field named `Name`. It is a required Entry Identity and
Short Text. The user can immediately rename it. Templates such as Reading or
Chess may preconfigure fields, but templates are optional and never create
sample data.

### Field rules

- Every Track has at least one Field.
- One or more Fields form the Entry Identity. Every identity Field is required,
  and identity Fields can use any Field type. Their formatted values are joined
  in Field order for lists, Search, accessibility, and duplicate review.
- Additional Fields may be optional or required.
- There is no hard maximum. The editor remains lazy and scrollable at 100
  Fields. A quiet advisory may say `Long Entry forms take more time to fill`,
  but it never blocks saving.
- Fields can be reordered. Generated Entry forms follow that order.
- Any Field may request `Show Label in Entry List`; the compact card renders a
  bounded supporting preview while the full Entry retains every preference.
- Renaming or reordering preserves values.
- A Field type can change only while it has no saved values.
- Removing a Field with values names the affected Entry count and permanently
  deletes those values only after confirmation.
- The final Field cannot be deleted. The last Entry Identity Field cannot be
  deleted or deselected until another Field becomes part of the identity.
- A Field referenced by an Automation cannot be deleted or type-changed until
  the Automation is retargeted or removed. The UI provides both recovery
  actions.

### Field types

#### Short Text

- Single-line input.
- Can be Primary.
- Operators: is, is not, contains, does not contain, is blank, is not blank.

#### Long Text

- Multiline input.
- Never Primary.
- Operators: contains, does not contain, is blank, is not blank.

#### Number

- Uses Whip's existing measurement type, unit, decimal precision, localized
  parsing, and inline custom-unit creation.
- Stores entered value/unit and canonical value.
- Operators: equals, not equal, greater than, at least, less than, at most,
  between, is blank, is not blank.
- Can contribute source values to dimension-compatible Goals.

#### Single Choice

- User-defined, ordered options with stable UUIDs.
- Operators: is, is not, is one of, is blank, is not blank.
- Removing an unused option is immediate. Removing an option used by Entries or
  Automations requires choosing a replacement or explicitly deleting affected
  values/rules. Option renames preserve identity and history.

#### Scale

- A discrete numeric scale with configured lower bound, upper bound, and
  increment. Presets are 1-5 and 1-10; an increment of `0.5` makes values such
  as `3.5` first-class rather than rounding them to integers.
- Entry uses a labeled slider plus decrement/increment controls instead of a
  dense row of value chips. Every path snaps to the configured choices, and an
  optional Scale can be cleared explicitly.
- The increment must land exactly on the maximum, may use up to six decimal
  places, and may produce at most 1,001 choices. That technical ceiling keeps
  accessibility semantics and rendering bounded without imposing a small
  arbitrary range.
- Optional endpoint labels, such as `Uncertain` and `Confident`.
- Stored as a unitless numeric value and supports Number operators and Goal
  aggregation.
- Called `Scale`, never `Rating`, so it can mean confidence, difficulty,
  enjoyment, or quality.

#### Date

- Local calendar date independent of the Entry Date.
- Operators: on, before, on or before, after, on or after, between, is blank,
  is not blank.

#### Yes/No

- Three states when optional: unanswered, Yes, No.
- Two states when required.
- Operators: is Yes, is No, is unanswered, is answered.

## Track list and detail design

Track rows/cards remain flat, dense enough for scanning, and use no decorative
color metadata:

```text
[icon] Books Read                         Add Entry  Edit
       Main · 12 Entries
       Latest: The Dispossessed · Aug 21
```

- Clicking the row opens Track details.
- `Add Entry` is the only quick-log action.
- The shared pencil edits exactly that Track.
- The latest Entry preview uses the composite Entry Identity and a bounded supporting
  value.
- Narrow layouts move `Add Entry` below the identity row instead of truncating
  the name or shrinking touch targets.

Track detail is one adaptive destination with:

```text
Entries | Insights | Automations | Options
```

The shared scrolling destination control is used without edge fades or
shadows.

### Entries

```text
Chess Openings Learned
7 Entries · Main

[ Add Opening ]

Opening                                      Search  Sort/Filter

Caro-Kann Defense                                      Edit
Black · Confidence 4 · Aug 20
Classical Variation

Queen's Gambit Declined                                Edit
Black · Confidence 3 · Aug 17
```

- The action label derives from the first Entry Identity Field: `Add Opening`.
- Search covers the composite identity, text, choices, and formatted values.
- Search uses the existing scoped Search affordance; there is no permanent
  Search/Filter/Select button row.
- Sort and Filter share the compact list-options control. Active filters appear
  below as removable rectangular chips with a Clear All action.
- Default sort is Entry Date descending. Other sorts include Entry Identity,
  creation date, and every scalar Field. Long Text is not sortable.
- Filter uses the same typed operators as Automation conditions.
- Clicking an Entry opens it. The pencil edits the exact Entry. Delete is in
  the Entry editor's separated danger zone and states affected Goal progress.
- Entry scroll position, query, sort, and filters survive editor round trips
  and posture changes.

### Entry editor

Generated forms use schema order and shared controls:

```text

[ 1. e4 c6 2. d4 d5 ...                         ]
```

- Primary is focused first. IME Next follows visible Field order.
- Entry Date is always present, defaults to Whip's current local date, and can
  be backdated. It is source-event metadata, not a user Field.
- Required errors appear at their Field and remain visible.
- A successful Add closes the editor and offers `Add Another` in operation
  feedback rather than rendering two permanent save buttons.
- Duplicate Primary values are allowed, with a non-blocking warning and direct
  links to possible matches.
- Unsaved-change protection, loading ownership, failure recovery, and Back
  behavior use the shared editor contract.

### Insights

Insights are projections and never stored as a second source of truth.

- All Tracks: total Entries, recent rate, first/latest dates.
- Number and Scale: entry count, sum, average, minimum, maximum, and trend.
- Single Choice: counts and percentages by option.
- Yes/No: Yes, No, and unanswered counts.
- Date: earliest, latest, and distribution over time.
- Text: no invented score; show only completion/search summaries.

Insight date range and typed filters reuse the same filter model as Entries.
No productivity score, sentiment inference, or judgmental copy is permitted.

### Automations

The tab groups rules by consequence:

1. `Goals Using This Track`.
2. `Capture From Tasks and Habits`.
3. `Follow Up After Entries`.

Every row reads as a sentence and exposes enabled state, current deterministic
eligible/skipped/contribution or prompt counts, Edit, and Remove. Disabled controls explain their
recovery path.

### Options

- Edit Track.
- Pin/Unpin on Home.
- Duplicate Structure. This copies Fields and Choice options, not Entries or
  Automations.
- Export Track CSV.
- Archive/Restore.
- Separated Danger Zone with Delete Permanently.

## Progress Automations: Track to Goal

Progress Automations extend `LinkSourceType` with Track and continue using the
existing Link Rule, Contribution, preview, exclusion, override, and metric
entry audit path. Do not build a parallel Track-only automation engine.

### Easy creation paths

From a Track, `Set a Goal` opens a guided builder and creates the Goal and
Progress Automation atomically:

```text
Set a Goal from Books Read

Measure
[ Count Entries                                 v ]

Include Entries where
[ Add Condition ]

Goal Name
[ Read 50 Books                                 ]

Target
[ 50                                            ]

Start History
[ From Goal Start                               v ]

Deadline
[ Optional                                      ]

Preview
12 eligible Entries · 12 Books of progress
```

From an existing Goal, `Add Progress Source` offers Track, then the same
measure/condition/history flow. The editor filters targets by unit and Goal
semantics before enabling Save.

### Measures and compatible Goal semantics

| User choice | Source event produced per eligible Entry | Compatible Goal behavior |
| --- | --- | --- |
| Count Entries | `1 count` | Build a Total, Reach a Target, Stay Consistent |
| Count Matching Entries | `1 count` after conditions | Build a Total, Reach a Target, Stay Consistent |
| Sum a Number/Scale Field | canonical Field value | Build a Total |
| Average a Number/Scale Field | canonical Field value | Meet an Average |
| Latest Number/Scale Field | canonical Field value | Reach, Reduce, Stay in a Range, Observe a Trend |
| Minimum Field Value | canonical Field value | Observe a Trend using Minimum aggregation |
| Maximum Field Value | canonical Field value | Observe a Trend using Maximum aggregation |
| Fixed Amount per Matching Entry | configured unit-compatible amount | Build a Total or Reach a Target |

`Sum`, `Average`, `Latest`, `Minimum`, and `Maximum` are guided user choices;
the underlying source remains one stable Field-value event per Entry and the
Goal owns aggregation. This preserves individual auditability and lets edits or
deletions reconcile one Contribution.

Advanced numeric transformation retains Whip's multiplier and offset only when
the source and target dimensions are compatible. The editor shows a natural
example before Save, such as `Each kilometre contributes 0.621 miles`.

### Conditions

Rules may contain any number of typed conditions and one top-level mode:

- `Match All` (AND).
- `Match Any` (OR).

Nested condition groups and user-authored expressions are excluded. Each
condition is `Field -> operator -> value`; dependent values sit directly under
the Field/operator choice. Blank optional Fields have explicit blank semantics
and never become zero, false, or an empty choice.

Example:

```text
Count Entries where all are true

Genre              is              History
Rating             at least        4
Entry Date          on or after     Jan 1, 2026
```

The rule summary becomes:

> Each Books Read Entry where Genre is History and Rating is at least 4 adds 1
> Book to Read 10 Great History Books.

### History and backfill

Creation requires one explicit history choice:

- New Entries only.
- Include since Goal start.
- Include since a chosen date.
- Include all Track history.

Preview reports:

- scanned Entries;
- eligible Entries;
- skipped Entries by reason, including blank source Field;
- total canonical contribution;
- first/latest eligible dates;
- unit conversion and transformation;
- target Goal impact.

Backfill commits only after confirmation. Cancellation leaves no partially
created rule or contributions. Large backfills expose operation progress and
remain idempotent.

Goal deadline affects pace and status; it does not silently delete late source
events. Date eligibility comes from the explicit history choice and conditions.

### Reconciliation rules

- A source-event ID includes stable Track, Entry, and Field UUIDs, never list
  positions or labels.
- Editing an Entry rebuilds only rules for that Track. Existing Contributions
  update in place.
- If an Entry stops matching, its Contribution and generated metric entry are
  removed.
- Deleting an Entry removes its Contributions and recalculates affected Goals.
- Restoring an undone deletion restores stable identity and Contributions.
- Exclusion and override state survives ordinary source edits while that source
  event still exists.
- Deleting the source event permanently deletes its exclusion/override audit;
  confirmation names affected Goals.
- Rules that reference removed Fields or options are blocked before the schema
  change; no silent invalid rule is stored.
- Rule rebuilds are deterministic after restore, Area movement, time-zone
  change, or app restart.

## Task and Habit integration

Task/Habit integration extends the existing Trigger system. The schema should
replace the narrow `autoCompleteTargetHabit` boolean with an explicit action
enum so consequences are representable and inspectable.

### Capture Automations: Task or Habit to Track

Use cases:

- Completing `Finish Current Book` prompts `Add Book` to Books Read.
- A successful `Practice a New Opening` Habit prompts `Add Opening` to Chess
  Openings Learned.
- A numeric Habit log can prefill a dimension-compatible Number Field.

Rule creation:

```text
Create Capture Automation

When
[ Task Completed                                v ]
[ Finish Current Book                           v ]

Then
[ Prompt to Add Entry                           v ]
[ Books Read                                    v ]

Prefill
Book Title        <- Task Title
Entry Date        <- Completion Date
Notes             <- Task Notes

Prompt Timing
[ Immediately                                    v ]

Notification                                    [Off]
```

Supported source events:

- Task completed or skipped, including stable recurring occurrences.
- Subtask completed.
- Habit succeeded, failed, skipped, or recorded.
- Track Entry added, for Follow-up Automations.

Supported prefill sources:

- Task/Subtask title and notes.
- Habit name, note, numeric value/unit, and outcome.
- Event date.
- A configured constant compatible with the target Field.

Whip never fabricates a required value. Save remains disabled until every
required target Field is either mapped or intentionally left for the prompt.

### Durable pending prompts

A snackbar alone is not reliable. Every source occurrence creates one durable,
deduplicated pending prompt:

- Foreground completion shows `Task Completed · Add Book`.
- If ignored, `Pending Entries` appears at the top of All Tracks and on the
  affected Track.
- A user can Add, Remind Later, or Dismiss.
- A notification is sent only when the rule explicitly enables notifications;
  permission is requested at that control, never merely by opening Tracks.
- Quiet hours and delay reuse existing Trigger behavior.
- Undoing the source event removes an unfulfilled pending prompt.
- Saving an Entry fulfills the occurrence. The saved Entry is independent and
  is not deleted if the Task/Habit is later undone.
- The Entry retains a source snapshot for explanation, even if the source item
  is later deleted.

Automatic creation of structured Entries is excluded. A prompt may be only one
tap when all Fields are prefilled, but the user confirms the durable fact. This
avoids fabricated required data and surprising deletion semantics when a Task
completion is undone.

### Follow-up Automations: Track to Task or Habit

A filtered Track Entry can trigger the existing Task/Habit prompt behavior:

- After adding a Book, prompt an existing `Write Book Notes` Task.
- After logging an Opening with Confidence below 3, prompt `Review Opening`.
- After an eligible Entry, check off an existing Habit only when the user
  explicitly selects that consequence and the Habit uses Check Off.

Follow-up rules use the same typed conditions as Progress Automations. One
Track source event produces one Trigger occurrence. Rebuild and deletion remove
unfulfilled occurrences. Automatically checking a Habit remains idempotent and
retains source provenance.

Do not add arbitrary Task templates or create a new Task definition for every
Entry in the first implementation. Follow-ups target existing Tasks/Habits.

## Automation UX contract

Every Automation editor uses this causal sequence:

1. `When` source and source event.
2. Immediately adjacent source conditions.
3. `Then` target and consequence.
4. Immediately adjacent mapping/value settings.
5. History, timing, quiet hours, and notification behavior.
6. Human-readable preview and impact summary.

No rule is represented only by technical enums. Examples:

- `Each eligible Entry adds 1 Book to Read 50 Books.`
- `Use Reading Time and average eligible Entries for Average 30 Minutes.`
- `When Finish Current Book is completed, prompt to add a Books Read Entry.`

Disabled controls always explain both cause and recovery. Changing an enabling
choice removes or confirms deletion of dependent state; it never leaves hidden
conditions or mappings in the database.

The Automations tab shows failures and stale references as actionable rows, not
silent no-ops. `Fix Automation`, `Choose Another Field`, and `Remove Automation`
are explicit recovery actions.

## Areas, lifecycle, and deletion

- A Track belongs to exactly one active Area, initially the current/default
  Area.
- Area scope affects Track lists, Search, Automation pickers, and Home pinned
  Tracks. Pickers default to the current Area and offer `All Areas` explicitly.
- Area move moves the Track and all its Entries as one object. Entries never
  move separately.
- Area delete/merge impact summaries add Track and Entry counts. The existing
  move-to-another-Area versus permanently-delete choice includes Tracks.
- Deleting a Goal removes Progress Automations targeting it without deleting
  the source Track.
- Deleting a Task/Habit removes Capture rules referencing it and unfulfilled
  prompts, without deleting confirmed Entries.
- Archiving a Track blocks new Entries by default and pauses Capture rules that
  target it. Historical Goal Contributions remain because their evidence still
  exists. Restore does not silently re-enable rules the user disabled manually.
- Permanent Track deletion shows exact Entry, Field, option, Progress
  Automation, pending prompt, affected Goal, and Trigger counts. The domain
  deletion coordinator removes generated Goal metric entries before deleting
  rules/source records.
- There is no soft-deleted or disabled schema residue. Archived Tracks are a
  visible supported lifecycle state, not legacy storage.

## Data architecture

### Source tables

`tracks`

- Room ID and stable UUID.
- Name, description, icon, Area ID, tags.
- Pinned, archived, position, created/updated timestamps.

`track_fields`

- Room ID and stable UUID.
- Track ID, name, type, order, required, Primary, show-in-list.
- Number dimension/unit/precision configuration.
- Scale bounds, increment, and endpoint labels.

`track_choice_options`

- Room ID and stable UUID.
- Field ID, label, order, created/updated timestamps.

`track_entries`

- Room ID and stable UUID.
- Track ID, Entry Date, creation instant, update instant.
- Optional source occurrence ID and immutable source explanation snapshot for
  confirmed Capture prompts.

`track_values`

- Room ID and stable UUID.
- Unique Entry ID plus Field ID.
- One typed value: text, canonical/entered number and unit, date, boolean,
  choice-option ID, or scale value.
- Repository and database constraints require the value column to match the
  Field type.

`track_entry_search`

- Rebuildable FTS projection of Primary/text/choice/formatted values.
- Updated transactionally and fully rebuildable after restore.
- It is a cache, never the source of Entry data.

### Automation extensions

- Add `Track` to `LinkSourceType`.
- Add source metrics `EntryCount` and `FieldValue`; keep Goal aggregation in
  the Goal domain rather than storing aggregate snapshots in Tracks.
- Add typed Link-rule condition rows referencing stable Field/option UUIDs.
- Replace Trigger's boolean special case with an explicit Trigger action enum:
  `PromptTask`, `PromptHabit`, `CheckOffHabit`, `PromptTrackEntry`.
- Add `Track` to Trigger target/source types.
- Add Capture mapping rows from source properties/constants to Track Fields.
- Extend Trigger occurrences with fulfilled Entry identity and reminder state.

Link conditions and Trigger conditions use explicit foreign keys rather than a
generic owner-type/value table. Duplication is preferable to losing referential
integrity in a polymorphic rule table.

### Integrity invariants

- At least one required Entry Identity Field per Track. The database guard
  enforces required identity Fields; repository validation enforces the non-empty set.
- Every Entry belongs to one Track; every value belongs to a Field in that same
  Track.
- At most one value per Entry/Field.
- Required Fields are present before an Entry transaction commits.
- Numeric source/Goal dimensions match after canonical conversion.
- Choice values reference an option in the value's Field.
- One Contribution or Trigger occurrence exists per rule/source-event ID.
- Labels and list positions are never identity.
- Entry CRUD and automation reconciliation are transactional from the user's
  perspective.

Do not mirror every Track value into `metric_entries`. Track tables are the
source of truth. Only Link Contributions create target Goal metric entries, as
the current auditable Link architecture expects.

## Search, filters, and performance

- Add `Track` and `Track Entry` to Unified Search. Track Entry results display
  the Primary value and parent Track; selecting one opens that Track and Entry.
- `area:`, `before:`, and `after:` syntax applies to Track/Entry results.
- Do not add `track:` or typed Field query syntax without a demonstrated need.
  The implemented graphical typed-filter model is the intentional product
  boundary, not deferred work.
- Track Entry lists use repository paging/lazy rendering, not an in-memory copy
  of all Entries.
- Index Track ID/date, Field ID, canonical numeric values, choice option, and
  Automation source references.
- An Entry edit reconciles only Automations for its Track and source event.
- Rule edits may perform a full Track backfill under the global operation
  progress indicator. Cancel rolls back the atomic transaction rather than
  retaining a partial rule or partial contributions.
- Performance acceptance covers 100 Fields, 10,000 Entries in one Track, 100
  Automations, and concurrent Goal rebuilds without duplicate contributions.

## Backup, restore, import, and export

- Bump Room schema and backup database version together.
- Add all Track and Automation tables to complete backup, preview counts,
  checksum, restore ordering, merge ID remapping, and rollback envelopes.
- Restore rebuilds FTS, Progress Contributions, pending prompts, reminders, and
  WorkManager ownership before success.
- Duplicate stable UUIDs fail preview or merge safely.
- Track CSV export uses one column per current Field plus Entry Date and stable
  Entry UUID. Choice exports labels; Number exports entered value/unit and a
  documented canonical column when relevant.
- CSV is interoperability, not complete backup. Export includes stable Entry
  identity, dates, current Fields, and entered/canonical numeric values. Import
  provides explicit schema and unit-column mapping, validates every row in a
  preview, and commits all-or-nothing; it never silently creates or changes
  Fields or Choice options.

No new Android permission is required for Tracks. Notifications remain optional
and are requested only at an enabled notification control.

## Adaptive and visual design contract

- Use Whip's shared rectangular controls, restrained corners, unified accent,
  flat surfaces, and outline hierarchy. Tracks add no arbitrary color field.
- One action is visually Primary per state.
- Page identity precedes local controls. Inactive filtering machinery consumes
  no permanent row.
- Action labels are centered; content and Field values follow readable
  start-alignment. Touch targets remain at least 48 dp.
- Closed phone: All Tracks and Track detail are full-height destinations;
  editors use the standard full-height adaptive editor.
- Open Fold: Track list is the master pane and selected Track/Entry is the
  detail pane. Editors stay wholly in their pane unless intentionally
  full-screen and never straddle the hinge or create a mismatched system-bar
  width.
- Selected tabs scroll into view without gradient edge fades or shadows.
- Layout survives 2x font scale, RTL, keyboard navigation, screen readers, and
  the closed/open Fold posture without concatenated labels or unequal padding.

Accessibility semantics include:

- `Books Read, 12 Entries, latest August 21. Open Track.`
- `Confidence, 4 of 5, Confident.`
- `Read 50 Books, 12 of 50 Books, 24 percent, progress source Books Read.`
- Automation summaries as complete sentences, including enabled/error state.

## Instructional and naming audit

Before release, search all user-facing copy and documentation for:

- `Track a Trend`, which becomes `Observe a Trend`;
- `Log Goal Value` or `measurement` where an Entry/contribution is meant;
- `Link Progress`, which becomes the clearer `Add Progress Source` or
  `Progress Automation` in the applicable flow;
- generic `item`, `record`, or `database` where the configured Entry Identity or
  `Entry` should appear;
- notification instructions that imply permission is required before a rule
  enables notifications;
- Settings directions for Track Fields, custom units, Search, backup, and
  Automations that no longer match their actual location.

The user guide must include one simple count example and one filtered numeric
example without presenting templates as required setup.

## Delivery sequence and exposure gates

### Phase 1: domain and persistence — complete

- Track/Field/option/Entry/value entities, DAOs, repository, validation, Area
  lifecycle, deletion coordinator, backup, and tests.
- No production navigation entry until the complete standalone CRUD flow is
  usable.

### Phase 2: standalone Track UX — complete

- Global Add, Home pinned section, All Tracks, adaptive detail, Field builder,
  generated Entry editor, Search, filter/sort, Insights foundation, archive,
  duplicate, CSV export, and accessibility.

### Phase 3: count-based Goal integration — complete

- `Count Entries`, typed conditions, Goal creation from Track, Add Progress
  Source from Goal, history preview/backfill, audit, exclusion, override, and
  deterministic reconciliation.

This is the minimum public exposure gate. Tracks should not ship as a Goal
source without standalone management, and should not ship as standalone logs
without the count automation that justifies their place in Whip.

### Phase 4: full numeric Goal integration — complete

- Sum, Average, Latest, Minimum, Maximum, Fixed Amount, unit conversion,
  transformation preview, blank handling, filter conditions, and all compatible
  Goal semantics.

### Phase 5: Task and Habit integration — complete

- Capture Automation editor, mappings, durable Pending Entries, delayed/quiet
  prompts, opt-in notifications, source undo behavior, and Context display.
- Track-source Follow-up Automations into existing Tasks/Habits and explicit
  idempotent Check Off behavior.

### Phase 6: mature insights and interoperability — complete

- Complete typed Insights, filtered summaries, large-data performance work,
  CSV import mapping/preview, and documentation.

Every phase ends with a clean schema and production reader for every persisted
field. Temporary compatibility tables, hidden flags, and abandoned partial
models are removed before merging. The numbered phases describe dependency
order for maintenance; none is an unfinished feature gate.

## Verification matrix

### Domain and calculation

- Every Field type, required/blank state, localized Number, units, Scale bounds,
  Choice identity, Date boundary, and Yes/No tri-state.
- AND/OR condition truth tables for every operator.
- Count, matching count, Sum, Average, Latest, Minimum, Maximum, and Fixed Amount
  with empty/missing values and unit conversion.
- Goal compatibility and dimension errors include recovery guidance.

### Repository and integrity

- Create/edit/reorder/rename/delete Field and option consequences.
- Entry create/edit/delete/restore, duplicate Primary values, source snapshots,
  and cascade behavior.
- Incremental and full rule rebuild idempotency.
- Entry edit stops/starts matching without duplicate contributions.
- Exclusion/override retention and source deletion behavior.
- Area move/merge/delete and Track archive/restore.
- Goal, Task, Habit, Track, Field, and option deletion coordination.
- Backup/restore/merge/remap/checksum/rollback and CSV escaping.

### Automation

- Each source occurrence creates one Contribution or pending prompt.
- Recurring Task occurrences never collide.
- Habit numeric values preserve dimension and local date.
- Undo removes unfulfilled prompts; confirmed Entries remain.
- Quiet hours, delay, dismissal, reminder, notification permission timing, and
  process restart.
- Backfill preview exactly matches committed results and cancellation commits
  nothing.

### UX and accessibility

- Blank, one Entry, dense Entries, 100 Fields, 10,000 Entries, empty filtered
  results, validation errors, stale Automation, and destructive confirmations.
- TalkBack names, roles, state descriptions, traversal, edit/delete actions,
  Scale semantics, and error announcements.
- Keyboard Tab/Shift-Tab, Enter, Escape, IME Next/Done, and hardware shortcuts.
- 2x font scale, RTL, narrow phone, closed Fold, open Fold, tabletop Fold, dark
  and light themes.
- No duplicate Search/Add controls, edge fades, unintentional modal stacking,
  mismatched system bars, clipped Primary labels, or unequal navigation padding.

Instrumentation runs only on an emulator or dedicated test device. Manual
physical-device validation uses the signed release and fresh live screenshots;
checked-in historical screenshots are not evidence.

## Definition of done

Tracks are complete only when a user can:

1. Create a Track with an arbitrarily long typed schema and one named Primary
   Field.
2. Add, find, understand, edit, export, and permanently delete Entries on both
   compact and Fold layouts.
3. Create a Goal from Entry count or any supported numeric aggregation, preview
   history, and inspect exactly which Entries changed progress.
4. Edit/delete source Entries and receive deterministic Goal reconciliation.
5. Receive and recover durable Task/Habit-to-Track prompts without phantom
   entries or surprise notification permission requests.
6. Trigger explicit Task/Habit follow-ups from filtered Entries.
7. Move/archive/delete Areas and domains without orphaned values, rules,
   contributions, prompts, jobs, or search projections.
8. Backup, restore, merge, and locally test the entire graph.

The product test is simple: Whip lets users define what evidence matters and
connect that evidence to action and outcomes, but it never asks them to build a
database application.
