# Whip UX Audit — 2026-08-22

> Follow-up: the later 46-screen live audit and multi-perspective debate found remaining architectural issues. Where recommendations conflict, [`UX_ARCHITECTURE_IMPLEMENTATION_PLAN_2026-08-22.md`](UX_ARCHITECTURE_IMPLEMENTATION_PLAN_2026-08-22.md) is authoritative.

This pass used fresh screenshots from the installed release on a Samsung SM-F976W in open-fold mode plus current source inspection. Checked-in historical screenshots were not used as evidence. Every retained capture is cropped to exclude the Android status bar and task/navigation bar.

## Fold App Bar

- **Problem:** The split-view app bar exposed Add, Expand, Search/Agenda, More, and Settings at the same time. Global actions competed with the page's own controls.
- **Principle:** Preserve one obvious primary action and progressively disclose secondary actions.
- **Scope:** Home, Tasks, Habits, Goals, Gym, and Settings in book-fold split view.
- **Change:** Keep contextual Add visible. Consolidate Search, Open Agenda, Expand Content, and Open Settings under one consistent overflow menu. Settings keeps an explicit Close action.
- **Reasoning:** The app bar now reads as navigation plus one contextual action, while infrequent global utilities remain reachable in one predictable place.
- **Verification:** Fresh captures `after/live/home.png`, `after/live/tasks.png`, and `after/live/settings.png`; `AdaptiveWhipScreenTest.bookFoldUsesHingeAwareSupportPaneAndPersistentNavigation` covers the menu and expansion paths.

## Fold Support Pane

- **Problem:** The complete four-card dashboard repeated beside every destination, using half of the open-fold display for unrelated summaries.
- **Principle:** Supporting panes should provide local context, not duplicate global navigation or dashboard content.
- **Scope:** Tasks, Habits, Goals, Gym, and Settings in book-fold and tabletop layouts.
- **Change:** Home retains the full At a Glance dashboard. Empty destination panes now show only that destination's summary; populated destinations show their current items. Settings shows a concise contextual explanation instead of metrics.
- **Reasoning:** Each destination now uses the left pane to reinforce the work happening on the right.
- **Verification:** Fresh captures `after/live/tasks.png`, `after/live/goals.png`, and `after/live/settings.png`; adaptive UI coverage verifies unrelated summaries disappear on Tasks.

## List Toolbars

- **Problem:** Tasks stacked Search, Filters, and Select as equal page-like buttons. Search then inserted another row. Habits and Goals used similar functions with different labels and behaviors.
- **Principle:** Peer features should share one control grammar; temporary modes should replace normal tools instead of accumulating beside them.
- **Scope:** Task, habit, and goal list screens.
- **Change:** Added `SearchOrActionsRow`. Search replaces the action row while active. Task filtering is labeled **Filter & Sort**. Rare selection/reordering actions live in a vertical-ellipsis overflow. Active selection/reorder modes show a full-width mode header with Done.
- **Reasoning:** Navigation, filters, actions, and temporary modes are now visually distinguishable and behave consistently across domains.
- **Verification:** Fresh captures `after/live/tasks.png`, `after/live/tasks-search.png`, `after/live/habits.png`, and `after/live/goals.png`; `InteractionControlUiTest.contextualSearchReplacesActionsInsteadOfAddingAnotherRow` covers row replacement.

## Task Filtering and Selection

- **Problem:** Filter controls mixed sorting, grouping, and filters as identical chips; selected-task controls used the vague label “Options.”
- **Principle:** Use the control type that matches the decision and name the result, not the implementation.
- **Scope:** Task Filter & Sort dialog and task selection mode.
- **Change:** Sort By and Group By are single-choice selection fields. Actual filters remain chips. The toolbar and selection mode report the active count as **Filter & Sort · N**.
- **Reasoning:** Users can predict whether a control changes ordering, grouping, or membership before opening it.
- **Verification:** Compose semantics coverage opens **Filter & Sort Tasks** and verifies the revised task toolbar path.

## Enabling Controls and Dependent Settings

- **Problem:** Settings enabled by a choice could appear much later in an editor, obscuring cause and effect. The reported task-repeat case placed recurrence details after planning controls.
- **Principle:** Show consequences immediately after the control that causes them; explain unavailable dependent controls and how to enable them.
- **Scope:** Task schedule/repeat, habit and goal advanced options, Health Connect data sources, gym machine/load definition, and routine prescription fields.
- **Change:** Dependent blocks now follow their enabling control. Added concise consequence notices. Task repeat settings appear directly under Schedule and before Planning Estimate and Effort. Health-backed habit fields are visibly locked to their source definition. Routine and gym disclosures describe exactly which fields become available.
- **Reasoning:** The editor order now communicates causality and lets users form a correct mental model without trial and error.
- **Verification:** Fresh capture `after/live/task-repeat-dependency.png`; `EditorDependencyUxTest` covers notices and blocked-state recovery guidance.

## Empty States and Capture Guidance

- **Problem:** Empty task and goal screens repeated creation instructions already represented by visible controls. Task quick-capture helper text was cramped against the field and did not explain that the arrow opens an editor.
- **Principle:** Empty states should state the condition once; helper copy should explain the consequence of the nearby action.
- **Scope:** Home, Tasks Today, and Goals Active.
- **Change:** Removed duplicate “use +” guidance and the second goal empty-state line. Task capture now uses a separated helper: “Opens the full task editor before anything is saved.”
- **Reasoning:** The screens retain useful orientation while shedding redundant instructional density.
- **Verification:** Fresh captures `after/live/home.png`, `after/live/tasks.png`, and `after/live/goals.png`.

## Naming and Visual Consistency

- **Problem:** Action capitalization, effort labels, selected colors, and pill/rectangle shapes varied across sections.
- **Principle:** Equivalent objects should use equivalent names, geometry, state color, alignment, and semantics.
- **Scope:** Shared buttons, toolbar actions, filter chips, selection fields, editor choices, gym labels, and task effort.
- **Change:** Shared Whip controls use rectangular shapes and a single selected-color treatment. Toolbar chrome is title-cased centrally. Effort is consistently **Light / Medium / High** under the **Effort** heading. Stored identifiers map to canonical labels such as **Check Off**, **Warm-up**, **Back-off**, and **Estimated 1RM**.
- **Reasoning:** Consistency removes relearning between sections and makes state easier to scan.
- **Verification:** `InteractionConsistencyTest`, `InteractionControlUiTest`, and shape tests cover canonical labels, alignment, touch targets, roles, selected state, and rectangular geometry.

## Permissions and Inspection Safety

- **Problem:** A launch-time notification prompt would interrupt screenshots and automated inspection.
- **Principle:** Ask for permissions at the moment a user enables the feature that needs them.
- **Scope:** Notifications and automated/live inspection.
- **Change:** Notification permission remains action-triggered by reminder/timer setup or Settings; it is not requested on app launch. Permission-denied creation journeys remain supported.
- **Reasoning:** The default app journey stays inspectable and users understand why a permission is being requested.
- **Verification:** The fresh cold-launch audit completed without a permission dialog; `ProductivityCreationJourneyE2ETest` explicitly exercises notification permission denied.
