# Queued external Task shares after managed process death

`replay.py` sends two real `ACTION_SEND text/plain` intents to Whip's exported `MainActivity` on a disposable API 34 emulator. The second arrives while the first unsaved draft is open, causing the native “Review New Task Request?” queue dialog. Both exact Task titles are absent from Room. The driver backgrounds Whip, makes Settings foreground, lets Android kill Whip's stopped process, and refocuses the original task under a new PID. The queue dialog returns. “Keep Editing” reveals the retained first draft and waiting notice; saving it opens the second draft, then saving that leaves exactly one of each Task in Inbox.

The accepted `run-api34/proof.json` records task 1037, PID 7070 to 7229, and exact one-row counts for both unique titles. Five original 1080×2400 PNG/XML pairs—queued before/after the kill, first draft with waiting notice, second draft, and both saved in Inbox—were individually inspected. Both drafts, actions and final rows are legible, with no clipped decision/action. All five XMLs have zero Whip-owned `NAF=true` nodes. Supplemental states `platform.share.queue.dialog`, `.after-process-death`, `.first-waiting`, `.second-draft`, and `.saved-pair` map to those five captures outside the 528 in-app catalog.

The replay is guarded to an emulator/API 34, requires completed Setup and current debug APK, and only adds uniquely named synthetic Tasks. No production code, data schema, backup format, version, owner phone or release changed. This closes the two-share/process-death journey on Pixel API 34, not queue overflow under death, other MIME types, all launchers/devices or whole-product acceptance.
